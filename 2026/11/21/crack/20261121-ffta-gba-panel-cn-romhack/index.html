FFTA GBA 汉化实战：8 个日文 UI 标签的中文替换与 ARM Hook 架构

发表于 2026-11-21

《最终幻想战略版 Advance》（FFTA）的熊组汉化版里，人物状态面板、编成物品页、商店购买与卖出页还残留着 8 个日文标签：いどう / ジャンプ / かいひ / 武器こうげき / ぼうぎょ / 魔法のつよさ / ぼうぎょ / スピード。目标是把它们全部换成中文，并且不能破坏同一套 tilemap 上的数值、物品名、单位列表和菜单。

这件事的难点不在”翻译”，而在于这些标签根本不是字符串。它们由游戏自带的比例字体引擎在进入画面时逐像素写进 VRAM 的动态瓦片里，tile 分配每次进画面都可能不同，相同假名还会跨标签共享瓦片。常规的”找文本表 → 改编码”路线在这里完全走不通。

最终的方案是第三代架构：IRQ Hook + 逐格内容校验 + 私有瓦片重定向。它一个字节都不改游戏原有的字形瓦片，只在”当前格子的 tile 索引等于预期值”时，把这一格指向我们自己的中文瓦片。四个界面最终全部通过 mGBA 真机截图验证，并产出 3685 字节的 IPS 补丁。

先说结论

  • ROM：A.gba，10,361,856 字节，SHA256 552600D9…59550A44
  • 入口：ROM 0xFC 改成 E51FF004（ldr pc, [pc, #-4]），0x100 放 Hook 地址 0x089B9540
  • Hook：240 字节（代码 200B + 字面量池 40B），每帧执行一次
  • 私有瓦片：68 个，2176 字节，落在 CBB2 的 0x350-0x393，目标 0x0600EA00
  • 表：P 表 107 项（856B）、S 表 84 项（672B），每项 8 字节
  • 补丁：ffta_panel_cn.ips，3685 字节，35 条记录，应用回原版 ROM 后与交付 ROM 逐字节一致

一、这 8 个标签为什么不是”字符串”

GBA 的 2D 显示单位是 8×8 像素的瓦片（tile）。每个 BG 层有一张 tilemap，表项是 16 位：

位 含义
0-9 tile 索引（0-1023）
10 水平翻转
11 垂直翻转
12-15 调色板 bank（0-15）

4bpp 模式下每个瓦片 32 字节。游戏文本引擎的工作方式是：把假名字形逐像素写进 CBB（Character Base Block）里当前空闲的瓦片，然后修改 tilemap 表项指向这些瓦片。

flowchart LR
    A["ROM 字体与文本数据"] --> B["游戏文本引擎"]
    B -->|"逐像素写入"| C["CBB2 瓦片缓存 0x06008000+"]
    C --> D["BG tilemap 表项 tile 索引 + 调色板"]
    D --> E["GBA PPU 合成"]
    E --> F["屏幕像素"]

这个机制带来四个致命特性：

  1. 没有可改的字符串。在 ROM、EWRAM、IWRAM 里搜假名的编码序列全部阴性——字形是直接画上去的，标签文本不以字符串形式存在。
  2. 比例字体跨瓦片。每个假名约 10px 宽，一个标签会横跨多个瓦片的边界，相邻标签还会共享中间那一行瓦片。
  3. 相同假名共享瓦片。ぼうぎょ（防御）和 ぼうぎょ（魔防）日文完全相同，引擎去重后两行指向同一批 tile。在干净面板数据里能直接看到：两行的顶行（r13/r16）都指向 0x127-0x12C、bank 14，只有底行各自独立（r14 是 0x12F-0x134，r17 是 0x13F-0x144）。你改一个瓦片的内容，两行一起变。
  4. 分配每次都可能不同。实测同一商店页两次进入，84 个格子的 tile 分配 0/84 相同。任何”把预期 tile 写死在表里”的方案，进店第二次就可能全错。

更麻烦的是 CBB2 里没有”所有画面都安全”的区域：

区域 用途
0x04C-0x14A 状态面板字形流
0x0A1-0x2CF 商店购物流
0x1A0-0x228 角色头像
0x1B6 附近 装备名字形流
0x2D4 / 0x2E4 / 0x2EE / 0x2F4 装备页 BG0 引用
0x300-0x3FF 每帧 DMA 填充区

把中文瓦片随便塞进任何一段，都会在某个画面上表现成碎片或花屏。这就是为什么前面两代方案反复翻车。

二、逆向环境与取证手法

整个项目主要靠三种工具取证，互相校验。

2.1 mGBA 即时档解析

用户实机用 mGBA 0.10.5，即时档 .ssN 在 ROM 同目录。这个文件本体是 PNG，自定义 chunk gbAs 里 zlib 解压后就是 state body，总长 0x61000：

区段 偏移
头部 + CPU 0x000-0x7FC
调色板 PAL 0x7FC-0xBFC
VRAM 0xBFC-0x18BFC
OAM 0x18BFC-0x19000
IWRAM 0x19000-0x21000
EWRAM 0x21000-0x61000

锚点校验：IWRAM + 0x7FFC 是 0x03000F10，IWRAM + 0xF10 是 IRQ 调度器的首字。调色板用白色 BGR555 FF 7F 搜索定位。IO 寄存器偏移在部分状态下不稳定（DISPCNT 有时读成 0），所以画面识别更多依赖”已知寄存器值硬编码 + 逐画面验证”，而不是盲信即时档里的 IO 快照。

2.2 GDB Stub 注入

即时档保存的是存档当时的 IWRAM。如果存档来自原版或旧版本，0x03000F10 里还是旧 IRQ 向量，新 Hook 根本不会运行——页面会显示原版日文，很容易误判为”补丁无效”。

解决办法是让 mGBA 带 GDB stub 启动：

continue 之前通过 write_mem(0x03000F10, rom[0xFC:0x1FC]) 把入口跳板和字面量写进 IWRAM，等效于一次真实开机拷贝。这样载入任何旧即时档都能强制运行当前 Hook。

2.3 自动按键与截图

mGBA 的 Qt/SDL2 窗口只对焦点窗口派发按键，后台 PostMessage 会被丢弃。所以脚本必须先把窗口抢到前台（force_focus()），再按虚拟键：

虚拟键 实际键 GBA 键
VK "A" = 0x58 X B（取消）
VK "B" = 0x5A Z A（确认）
VK 0x0D Enter START

F12 会把 PNG 截图写到 ROM 同目录，脚本捕获新增文件并归档到 analysis/shots/。BizHawk 2.11（mGBA core）则用于早期自动导航，但要注意它每次 launch 都是冷启动，而且 --load-state 会挂起 Lua 的 savestate.load。

三、三代方案：从”改指向”到”改内容”再到”校验后改指向”

这个项目一共经历了三代架构，每一代都是被上一代的真实故障逼出来的。

3.1 第一代：tilemap 静态重定向（v13-v20）

思路很直接：把中文切片放进一块”空闲”瓦片区，然后把 84 个格子的 tilemap 表项改成指向这些瓦片。面板页一度工作得很好（v17 用户确认中文显示正常）。

失败点有两个：

  • 空闲区并不空闲。v16 把 blob 放进 0x300-0x3FF，那正是每帧 DMA 填充区；v13/v15 用的 0x084+ 在其他画面被字形流占用。判断”零引用”必须扫描全部 4 层 BG 的 tilemap，而且要区分 CBB 空间（BG0/BG1 的 tile 索引是相对 CBB0 的，BG2/BG3 才是 CBB2，同一索引号指向不同物理 VRAM）。
  • 静态预期会过期。v19 实测商店两次进入的 84 格分配 0/84 相同，写死的 (addr, expected_tile) 第二次进店就全部失效，表现就是数字和标签乱码。

3.2 第二代：字形内容替换（v24-v26）

既然分配会变，那就不猜分配，运行时读当前格子的 tile，直接把中文切片的 32 字节写进游戏已经分配的那个瓦片。这样不需要空闲区，也不需要预期值，面板、商店购买/卖出都一度 8 标签全中文。

代价是跨页面污染：

  • 中文被写进共享瓦片后，编成列表的单位标签、商店列表、买/卖的幽灵数字 1 2 3 4 都会复用同一批 tile，于是出现碎片。
  • ぼうぎょ1（防御）和 ぼうぎょ2（魔防）共享底瓦片，一个瓦片只有一个内容位，两行不可能同时正确。v25 只能额外做 T3 局部重定向，把魔防顶行 6 格改到 0x130-0x135。
  • 这套方案本质上是”和游戏抢同一块画布”，只要还有别的页面复用这些瓦片，就不可能根治。

3.3 v25 崩溃：IRQ 里少保存一个寄存器

v25 真机进商店直接崩，mGBA 报：

0x5EC002E4 在 ROM 和所有即时档里都不存在。根因是 Hook 用 r6 暂存 0x3FF 掩码，但 push/pop 列表里漏了 r6：

GBA BIOS 在进入 IRQ 时只保存 r0-r3 和 r12，r4-r11 属于被中断代码的上下文，必须由用户 IRQ 处理程序自己保存。商店绘图主循环正好把指针放在 r6，被 VBlank 打断后 r6 变成 0x3FF，后续按错误指针取数直接飞掉。

运行时验证脚本载入 ss2、注入调度器、预设 r6=0x12345678 / r7=0x0BADF00D / r5=0xCAFE123，跑 0.6 秒读回：v25 的 r6=000003FF，且已出现 PC=2A002A00；v26 三次全部保持原值。修复只有 2 个字节——把 r6 加进 push/pop，并在构建期断言寄存器集合完全一致。

3.4 第三代：逐格内容校验 + 私有瓦片（v27 起）

核心转变：永远不写游戏已有的瓦片。

  1. 每帧先把 68 个中文切片拷进一块经过验证的私有瓦片区（CBB2 0x350-0x393，4 个干净存档的全部 BG 层零引用、内容全零）。
  2. 表项从”(addr, expected_tile)“升级成”(addr, expected_tile, new_tile)“。
  3. 读当前格子的 tile 索引，只有等于预期值时才把该格改成 (原调色板 | 私有 tile)；不相等就一个字节都不写。

这样做的直接结果是：其他页面、其他行、列表装饰、数字格子的 tile 都不匹配预期，Hook 自动跳过，不可能再产生中文碎片。同时 ぼうぎょ1/2 各自指向不同的私有瓦片，同形标签天然分离。

第一代 静态重定向 第二代 内容替换 第三代 校验+私有瓦片
需要空闲区 需要 不需要 不需要（私有区已验证）
分配变化 静态预期过期 运行时自适应 运行时自适应
跨页污染 无，但映射会错 有，共享瓦片 无，原瓦片零改动
同形标签 天然分离 无法分离 天然分离
结果 商店不可用 四界面仍乱 四界面全部通过

四、最终架构拆解

4.1 入口：只改 4 个字节

GBA 的 IRQ 向量链是：BIOS 跳到 0x03007FFC 指向的地址，游戏把它设成 IWRAM 0x03000F10；而 0x03000F10 是开机时从 ROM 0xFC-0x1FB 拷贝过来的调度器。因此改 ROM 0xFC 会同时影响”BIOS 直跳 ROM”和”跳 IWRAM 拷贝”两条路径。

Hook 被放在 ROM 尾部的零区 0x9B9540。选择 ROM 尾部而不是中段零区，是踩过坑的：v14 曾把代码放进 0x537C60 的 1728 字节零区，结果那段位于文本指针表 0x52DA6C-0x53B61C 内部，零字节是数组的 null 终止符，写入指令后游戏读表越界，冷启动正常、读档黑屏。

4.2 门控：用三个 BG 控制寄存器区分画面

Hook 每帧都跑，必须先判断”现在是不是我们的目标画面”。判据全部来自实测寄存器值：

flowchart TB
    A["VBlank IRQ → IWRAM 0x03000F10"] --> B{"DISPCNT bit13 = 0 ?"}
    B -->|"否（强制消隐）"| Z["pop 恢复"]
    B -->|"是（显示开启）"| C{"BG0CNT = 0x4C03 且 BG2CNT = 0x0B08 ?"}
    C -->|"是"| S["选 S 表 84 项（商店购买/卖出）"]
    C -->|"否"| D{"BG3CNT = 0x2A08 ?"}
    D -->|"是"| P["选 P 表 107 项（面板/编成/装备）"]
    D -->|"否"| Z
    S --> E["拷贝私有瓦片"]
    P --> E
    E --> F["逐格校验与重定向"]
    F --> Z
    Z --> G["恢复 r3 = 0x04000200，B 0x08000104"]

寄存器值的含义可以直接解出来：

  • BG2CNT = 0x0B08：map base = 11 → 0x06005800，char base = 2 → 0x06008000，4bpp，32×32。商店购买/卖出共用这套配置。
  • BG3CNT = 0x2A08：map base = 10 → 0x06005000，char base = 2，32×32。状态面板、编成列表、编成物品、装备页右侧 mini 面板共用。
  • BG0CNT = 0x4C03：作为商店分支的附加校验，把”同样是 BG2 0x5800”的其他页面排除掉。

DISPCNT 只测 bit13（forced blank），不比对整字。画面切换过渡帧里其他位可能变化，但这一位能可靠区分”显示中”与”消隐中”，避免在过渡帧乱写。

4.3 私有瓦片池

私有瓦片区选在 CBB2 的 0x350 起，VRAM 地址 0x0600EA00（0x8000 + 0x350 × 32）。v29 共 68 个瓦片，2176 字节，从 ROM 0x934E70 连续拷贝：

ARM 的 LDM/STM 一次搬 4 个寄存器 = 16 字节，所以循环次数是 2176 / 16 = 136。这里用 r9/r10/r12 当搬运暂存，r0 此时已经完成门控判断，可以复用。

私有瓦片的”安全”不是猜的，而是构建期断言：解析 4 个干净存档（面板/编成物品/购买/卖出）的 BGxCNT，按 map base、char base、尺寸枚举全部 tilemap 表项，算出被引用的绝对 tile 集合，要求 0x350-0x393 与集合无交集，且这 68×32 字节在 4 份 VRAM 里全为零。

这里有一个细节值得说明：and r12, r1, #0xF000 会同时清掉水平/垂直翻转位（bit10/11）。文字格的翻转位本来就是 0，所以安全；如果将来要处理带翻转的图形格，这里需要改成 #0xFC00。

另外，整个循环只比较 tile 索引，不比较调色板。调色板的一致性由表生成阶段保证（P 表直接从同一页面取预期值；S 表在内容匹配时强制调色板 bank 相等）。运行时不比对调色板，是为了让同一个中文瓦片能在不同调色板 bank 下复用。

4.5 返回路径

Hook 替换的是调度器的第一条指令。执行完必须回到调度器的第三条指令 0x08000104，并且恢复它期望的 r3 = 0x04000200：

v9 曾经在结尾写 bx 0x03000F10，跳回已经被补丁的调度器开头，于是 LDR PC → Hook → BX → LDR PC 无限循环。当时用 Lua 测试还”成功”了——因为死循环本身在反复执行拷贝，截图看起来正常，但真机第一次 IRQ 就冻死。这个坑也是后来坚持”每条分支目标都做反汇编抽查”的原因。

六、字形合成与排版

6.1 画布与切片

中文不是直接生成 8×8 瓦片，而是先画在一张 240×160 的单色画布上，再按 84 个原始格子的 (row, col) 切成 8×8 瓦片。这样跨瓦片的字形（比如”攻”的左半边落在上一格）才能正确拼接。

flowchart TB
    A["8 个标签文本"] --> B["240x160 单色画布 阴影 + 墨色"]
    B --> C["按 84 个原始格子切 8x8"]
    C --> D["84 个 4bpp 瓦片（原序）"]
    D --> E["内容去重"]
    E --> F["68 个唯一瓦片 = 2176B blob"]

字体用系统 SimSun 的 12px 内嵌点阵，PIL 直接命中点阵，不做缩放。每个字先渲染到 16×16 灰度图，取墨迹包围盒，再按目标高度删掉墨迹最少的多余行，得到 11px 字形。先画阴影（偏移 +1,+1）再画墨色，保证 4bpp 下标不越界。

6.2 调色板约束

瓦片只存颜色下标，最终颜色由格子的调色板 bank 决定。标签用色号 3（墨）/1（影）；在面板使用的 bank 13/14/15 里，色号 3 都是白色 F8F8E8，色号 1 是近黑色，所以同一个中文瓦片换 bank 仍然是白字。黄色标签用色号 7/8（bank 15 下是 F8E800 / B86800）。

这带来一个隐蔽限制：面板上有些空白格的原始 tile 是 0x0FE、调色板 bank 0。如果标签左移占用这些格子，格子仍保留 bank 0，中文就会显示成错误的颜色。所以”能左移到哪里”不仅受 tilemap 格子集合限制，还受调色板 bank 限制。

6.3 对齐：两次左移与”格子集合”边界

用户先后提了两次对齐需求：

  1. v28：武器攻击/魔法强度 左对齐到 x=16。
  2. v29：防御/魔防 与上面两行的最后两字对齐（即”攻击”/“强度”的起点）。

v28 之所以能直接到 x=16，是因为原日文 武器こうげき 本来就从 c2（x=16）起，格子都在 84 项表内。

v29 第一次尝试把防御/魔防也直接移到 x=16，真机只显示残字「御」「防」。对齐前的 v28 对照是这样的：

原因：原日文 ぼうぎょ 的顶行（r13/r16）只包含 c4-c9，c2-c3 不在 84 格集合里（底行 r14/r17 才从 c2 起）。P/S 表不会重定向顶行这两个格子，游戏原有的假名字形就露出来，与私有瓦片拼成残字。

最终取 x0 = 42，正好是”攻击”/“强度”两字的起点，仍然落在 c5 起的原格子集合内，只前移 2px：

这条经验可以推广成一句规则：基于”原格子集合”的重定向架构，标签的可移动范围由原标签的格子跨度决定；要跳出去，必须先扩充表，并为新增格子逐格取证预期 tile。

6.4 没有做的那一项

编成页底部还有 6px 的 START:アイテムソート / START:アイテムリスト。它不是 BG 文字，而是 3 个 OBJ 精灵拼成 80px（32×8 两块 + 16×8 一块），字符跨瓦片且字号只有 6px。中文在 6px 下无法辨识，改造成本与收益不成比例，因此保留日文。这也是文档里唯一明确标注为”不做”的项。

七、验证链

7.1 构建期断言

make_hook_v27.py 在写 ROM 之前会做五类检查，任一失败直接终止构建：

检查 内容
表地址 落在对应 BG map 窗口、2 字节对齐、地址唯一
表内容 expected tile 非零且 < 0x400；new tile 在 0x350-0x393
零区 blob/P/S/Hook 四个写入区在原版 ROM 中必须全零
寄存器 push/pop 集合相等，且覆盖全部使用寄存器（r0-r6/r9/r10/r12）
反汇编 所有 LDR 字面量目标、B/BNE 分支目标、返回目标逐条核对

最后一项不是形式主义。项目早期把 LDR 字面量的 imm12 当成”字偏移”编码，实际是字节偏移，导致 v9/v12 的门控读到垃圾。后来所有字面量都由构建器计算 imm = pool_byte_off - (slot*4 + 8)，并断言 4 对齐、< 0x1000。

7.4 像素差分

“看起来正常”不够，还要证明”只改了该改的地方”。

  • v27 vs 原版：差异集中在标签/页签区域，差分像素 3178 / 2847 / 2871（面板/购买/卖出），物品名、价格、数量、HP/MP、数值列零差异。
  • v28 vs v29：差异限定在 x=42-68, y=104-139，正好是防御/魔防两行；其余区域零差异。

差分也踩过坑：直接拿 t4_01.png 和 v28 截图差分会把 bbox 拉到 y=33，因为两张不是同一画面/同一动画帧。正确做法是用同一个 ss4 分别跑 v27 和 v28，同状态对比。

7.5 可复现构建与 IPS

  • 二次构建 A_v29_check.gba 与 A_v29.gba 逐字节一致（length 10361856，equal True），证明交付 ROM 就是构建器产物，没有手工补丁。
  • IPS 生成：逐字节找差异区段，间隔 ≤ 4 字节的区段合并，单条记录超过 0xFFFF 就切分；写入 24 位偏移 + 16 位长度 + 数据，最后 EOF。

生成后再用独立的 IPS 应用函数回放一遍，和交付 ROM 比较。v29 的结果是 3685 字节 / 35 条记录 / PASS。

十、方法论总结

这个项目最后能稳定下来，靠的不是某个”神级技巧”，而是四件事：

  1. 把 UI 文本当渲染结果，而不是数据。 找不到字符串时，不要继续在 ROM 里翻编码表，先去看 tilemap 和 CBB，确认它是怎么被画出来的。
  2. 用寄存器做门控，而不是用地址猜画面。 DISPCNT/BG0CNT/BG2CNT/BG3CNT 的组合是画面身份的唯一可靠来源；同一段 VRAM 在不同画面含义完全不同。
  3. 不做盲写，做逐格校验。 (addr, expected, new) 三元组把”重定向”变成一个幂等、可跳过、可自动容错的操作；未命中就不写，任何页面都不会被写坏。
  4. 把不变式放进构建器。 零区、寄存器集合、字面量目标、跨页命中、私有瓦片零引用——这些断言让”构建失败的次数”替代了”真机翻车的次数”。

最终效果是四个界面、状态页、编成列表、装备槽页全部中文且无乱码，IPS 补丁 3.6KB，可复现构建，可回放验证。剩下 6px 的 OBJ 提示保留日文，是一个明确权衡后的取舍，而不是遗漏。
